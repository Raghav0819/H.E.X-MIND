# Closing H.E.X Mind's gaps with proven patterns

H.E.X Mind's topology (ADK orchestrator, CrewAI crews over A2A, shared blackboard, observability UI) is more elaborate than most state-of-the-art coding agents, which are mostly single-agent loops with very good mechanics. The research points to one pattern: reliability gains come from execution-grounded verification, robust edit application, bounded context, and measurement, not from more roles. Systems like OpenHands, Aider, Cline, mini-SWE-agent and Agentless are strong where H.E.X Mind is probably thin: edit formats, repo maps, checkpoints, sandbox hardening and a regression eval harness. H.E.X Mind is probably strong where they are thin: typed telemetry, A2A-aware tracing and role topology. **The highest-value adoptions are an edit-format layer with fuzzy application, a hardened no-network test container, a small in-house eval harness, and A2A conformance fixes (security schemes, artifacts, streaming, cancel); nearly all of them need only ADK, CrewAI, A2A and plain Python.** Two caveats govern everything below. First, the researchers did not read H.E.X Mind's source code; every "missing X" claim is an inference from the project description and must be checked against the repo. Second, version and benchmark numbers in the notes conflict in places, and those conflicts are flagged where they matter (a2a-sdk 0.3 vs 1.x, ADK 1.x vs 2.x, SWE-bench scores, free-tier limits).

## Where the field differs: pipelines and single loops, not role count

The "software company" systems use fixed role pipelines. MetaGPT models a product manager, architect, project manager and engineer around "Code = SOP(Team)", and ChatDev 2.0 (released 7 Jan 2026) moved to a YAML-configured, visual-canvas workflow platform ([MetaGPT](https://github.com/FoundationAgents/MetaGPT), [ChatDev](https://github.com/OpenBMB/ChatDev)). The leading coding agents are structurally different: OpenHands, mini-SWE-agent, Aider, Cline and Claude Code are essentially single-agent loops (Claude Code adds subagents with separate context windows), while Agentless dispenses with an agent loop and runs fixed localize, repair and validate phases, reporting **32.00% on SWE-bench Lite at $0.70 per issue** in 2024 ([Agentless](https://arxiv.org/abs/2407.01489)). H.E.X Mind's Planner, Coder, Reviewer pipeline sits between these: closer to Agentless and to AgentCoder (programmer plus executor feedback loop) than to a free-form loop ([AgentCoder](https://arxiv.org/abs/2312.13010)). That is a defensible fit for weak free-tier models, because the model never has to choose its own actions.

The evidence on what improves code quality favours execution-grounded loops over extra roles. AgentCoder's independent test designer plus executor reported 96.3% pass@1 on HumanEval with roughly 40 to 70% fewer tokens than the prior state of the art ([AgentCoder](https://arxiv.org/abs/2312.13010)), and SWE-Search's MCTS with value and discriminator agents gave a 23% relative improvement across five models ([ICLR 2025](https://www.iclr.cc/virtual/2025/poster/30299)). The MAST failure taxonomy (1,642 annotated traces, 14 failure modes) found that multi-agent gains over single-agent baselines are often minimal, and that failures cluster in specification, inter-agent misalignment and task verification ([MAST](https://arxiv.org/html/2503.13657v2)). Self-repair by a model critiquing its own code is often no better than simply sampling more, and a stronger model as the feedback source helps ([Olausson et al.](https://arxiv.org/pdf/2306.09896)); this older GPT-3.5/4-era result implies that a qwen-class local model should not be its own reviewer. The notes found no controlled comparison of hierarchical manager versus flat pipeline for coding, so H.E.X Mind's topology is neither validated nor refuted by the literature. The practical reading: keep the topology, but make the sandbox test result, not the Reviewer's opinion, the success signal, and cap retries then escalate the model (Groq to Gemini) instead of looping.

On the project's own stack, both frameworks have moved fast and the notes suggest several capabilities a typical pipeline leaves unused. CrewAI (latest seen 1.15.31, 2026-10-27) added task guardrails, Flows with typed state, checkpointing with SQLite storage, `crewai eval` with per-role model overlays, planning mode and execution hooks. ADK (latest seen 2.13.0) added plugins, `AgentEvaluator` efficiency metrics, graph workflows and an SQLite memory service ([CrewAI changelog](https://docs.crewai.com/v1.15.31/en/changelog.md), [adk-python CHANGELOG](https://raw.githubusercontent.com/google/adk-python/main/CHANGELOG.md)). Whether any of this is already used is unknown, since the code was not inspected. One version trap matters: ADK 2.x supersedes the templated Sequential, Parallel and Loop agents with graph workflows and changes the Event schema (`node_info`, `output`), which could affect TelemetryHub's event schema v2 ([ADK 2.0](https://adk.dev/2.0/index.md)). The notes do not establish which ADK line H.E.X Mind pins, and the release listings themselves are inconsistent (a 1.39.0 dated 2026-08-17 appears alongside 2.x entries; 2.12.0 vs 2.13.0 as latest), so the first step is to check the pinned version and decide deliberately.

## Single-agent mechanics are the largest probable gap

Aider's data is the clearest argument for an edit-format layer. It supports whole-file, search/replace, diff-fenced (mainly for Gemini, which often fails standard fencing), udiff and architect/editor splits, choosing a default per model ([Aider edit formats](https://aider.chat/docs/more/edit-formats.html)). In Aider's own 2023 GPT-4 Turbo test, unified diffs cut lazy "rest unchanged" output about 3x (SEARCH/REPLACE 20% vs unified diffs 61% on 89 tasks), and disabling flexible patch application caused about 9x more editing errors ([Aider unified diffs](https://aider.chat/2023/12/21/unified-diffs.html)); this is GPT-4-era evidence, so effect sizes on qwen2.5-coder:7b will differ. Even frontier models are not perfectly well-formed: top polyglot-leaderboard entries ranged from about 88% to 100% well-formed edits ([Aider leaderboards](https://aider.chat/docs/leaderboards/)). For H.E.X Mind this suggests a per-model format table, a deterministic applier with fuzzy matching and precise error feedback, a hard reject-and-retry on lazy placeholders, and a logged edit-compliance metric. Related guidance from a 2026 preprint is to prefer parse, validate, repair over strict JSON-schema decoding on local models, since hard constraints can preserve validity while losing correctness ([The Constraint Tax](https://arxiv.org/pdf/2605.26128), unreplicated).

Context and recovery are the next differences. Aider's repo map gives a graph-ranked symbol summary at a default 1k-token budget ([Aider repomap](https://aider.chat/docs/repomap.html)); no controlled pass-rate delta was found, but the token saving is plausible under Groq and Gemini free-tier limits. OpenHands' `LLMSummarizingCondenser` keeps the first 4 events and a recent tail while a cheaper model summarises the middle, which suits Ollama's small windows ([OpenHands condenser](https://docs.openhands.dev/sdk/arch/condenser)). OpenHands also treats an append-only typed event log as the source of truth, with swappable local, Docker and remote workspaces ([OpenHands SDK](https://arxiv.org/abs/2511.03690)). Cline snapshots a shadow git repo after each tool use with restore options for files, task or both ([Cline checkpoints](https://docs.cline.bot/features/checkpoints)), and Jules waits for plan approval before any code change ([Jules docs](https://jules.google/docs)). Because H.E.X Mind already edits git worktrees, per-step commits and a "restore to step N" control, plus an editable plan-approval gate after the Planner crew, are nearly free by comparison. The Chroma blackboard needs care: the evidence is that short, verified summaries help (SWE-ContextBench: 26.26% baseline vs 34.34% with oracle-selected summaries, but 22.22%, below baseline, when the agent chose freely) and that four general memory systems mostly failed to beat no memory (11 of 12 pairings) ([SWE-ContextBench](https://arxiv.org/html/2602.08316), [VibeMemBench](https://arxiv.org/abs/2609.23570)). The oracle setting is an upper bound. So store only test-verified lessons, retrieve with a similarity threshold, inject nothing on weak matches, and measure memory on versus off in the eval harness; a null result is acceptable to report.

## Safety, measurement and cost: hardening the sandbox and proving quality

Sandboxing is where Docker alone leaves a cheap, concrete gap. Claude Code's sandbox restricts writes to the working directory, protects `.git/hooks` and shell config, routes network through a domain-allowlist proxy, and keeps git credentials outside the sandbox ([Anthropic engineering](https://www.anthropic.com/engineering/claude-code-sandboxing), [docs](https://code.claude.com/docs/en/sandboxing)). Adaptive attacks broke 12 published prompt-injection defenses with most above 90% success, and Meta's Rule of Two (at most two of untrusted input, sensitive access, state change or external communication) frames architecture as the mitigation ([Willison summary](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). Applied here: run the test container with `--network none` (an allowlist only for a separate install step), `--cap-drop ALL`, `no-new-privileges`, read-only root with tmpfs, pids, memory and CPU limits, a non-root user, a wall-clock kill, no Docker socket and no secrets in the environment ([OneUptime](https://oneuptime.com/blog/post/2026-02-02-docker-security-best-practices/view), secondary). Whether H.E.X Mind already does these is unknown. gVisor and Firecracker are stronger but awkward on Docker Desktop for Windows (unverified), so treat them as roadmap.

Evaluation is the artifact most likely to be missing and most valuable for grading. Public numbers are unreliable inputs here. OpenAI stopped reporting SWE-bench Verified in February 2026, citing flawed tests in 59.4% of 138 audited hard tasks (cited via a secondary summary because the OpenAI page returned 403) ([Pebblous summary](https://blog.pebblous.ai/blog/swe-bench-verified-retired/en/)). Scores for specific tools conflict across sources: mini-SWE-agent is above 74% on Verified per its README, while third-party boards cited by a search summary list 96 to 97% for frontier models, which the notes call unverified and unusually high ([mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent), [Vals.ai](https://www.vals.ai/benchmarks/swebench)); OpenHands is reported at 72.8% in a secondary summary and 77.6% in a GitHub issue ([OpenHands SDK](https://arxiv.org/abs/2511.03690v1)); MetaGPT's SoftwareDev executability is 3.75 vs 2.25 in one overview but 3.9 vs 2.1 in the paper appendix ([MetaGPT paper](https://arxiv.org/pdf/2308.00352)). The sensible conclusion is not to chase SWE-bench but to build a frozen suite of 15 to 30 Node.js tasks with hidden tests mounted only at grading time, run k=3 to 5 times per provider configuration, and report pass@1, a pass^k consistency number, latency, tokens, fallback counts and a few negative safety tasks (read `.env`, symlink escape, injected instruction). ADK's `AgentEvaluator` with `tool_trajectory_avg_score` covers trajectory regression and maps to the course's ADK criterion, though some LLM-judged metrics may need Vertex's paid service ([ADK evaluate](https://adk.dev/evaluate/)).

Cost control follows from the free-tier reality, and here the figures are the least reliable in the notes. Google states Gemini limits are per project, in RPM, TPM and RPD, reset at midnight Pacific, and not guaranteed; third-party daily figures conflict (about 1,500, 250, and reports near 20 per day) ([Google rate limits](https://ai.google.dev/gemini-api/docs/rate-limits), [DEV cheatsheet](https://dev.to/hiyoyok/gemini-api-cheatsheet-2026-free-tier-limits-models-and-endpoints-in-one-place-2god)). Groq free-tier limits were not researched. The advice is therefore to read live limits from provider headers rather than hardcode numbers. H.E.X Mind's Groq, Gemini, Ollama chain already matches the standard pattern of LiteLLM's Router (cooldowns, fallbacks, backoff) ([LiteLLM routing](https://docs.litellm.ai/docs/routing)); the improvements are a header-driven token bucket, per-role token budgets with a visible "budget exhausted" event, an exact-match response cache for eval reruns, and a cheap-first cascade that escalates only when sandbox tests fail. No quantified savings for cascades in coding were found.

## Observability and A2A: strongest area, with specific conformance and standards gaps

Observability is likely H.E.X Mind's best differentiator. The surveyed platforms (Langfuse, Phoenix, LangSmith, AgentOps, Logfire) share trace trees, token and cost tracking and evals, and differentiate on agent graphs and time travel ([ZenML](https://www.zenml.io/blog/langfuse-vs-phoenix), [LangGraph Studio](https://langchain-ai.github.io/langgraph/concepts/langgraph_studio)); none of the pages the researchers read mention A2A-aware views, so the two-lane A2A timeline with `traceparent` propagation appears unusual. The comparison material is mostly vendor-framed and no user study ranks views by debugging value. The cheapest additions are OTLP export mapping events to OpenTelemetry GenAI names (`invoke_agent`, `chat`, `execute_tool`, `gen_ai.usage.*`) into a local Phoenix at localhost:6006, a per-agent token and cost table, a latency waterfall, a read-only replay scrubber over the persisted event log, failure clustering, a diff view of agent file edits and a post-run LLM-as-judge ([Dash0 on GenAI semconv](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained), [openinference-instrumentation-crewai](https://pypi.org/project/openinference-instrumentation-crewai/)). The GenAI conventions remain at "Development" stability and moved to a separate repository in v1.42.0 (June 2026), so label the export experimental and pin versions. CrewAI has no native OTel; the OpenInference instrumentor gives nested spans but no separate model-call spans, so token columns may be empty without H.E.X Mind's own hooks ([Logfire agent frameworks](https://pydantic.dev/docs/logfire/integrations/agent-frameworks/)), and double instrumentation of ADK spans is a risk to test one at a time. The effort estimates for these items are the notes' judgement, not sourced.

For A2A, the central uncertainty is versioning. The spec reached a stable 1.0 in March 2026 (a secondary source gives 12 March) and the Python SDK is at 1.3.0 (2026-10-27); a2a-sdk 0.3.x is the previous generation, still supported by ADK through a compatibility mode ([A2A spec](https://a2a-protocol.org/latest/specification/), [a2a-python releases](https://github.com/a2aproject/a2a-python/releases), [ADK A2A](https://adk.dev/a2a/)). The 1.0 vocabulary changed substantially: `SendMessage`, `supportedInterfaces`, `TASK_STATE_*` enums, no `kind` discriminator, and protobuf-based SDK types with route factories replacing `a2a.server.apps` ([What's new in v1](https://a2a-protocol.org/latest/whats-new-v1/), [AAIF migration guide](https://aaif.io/blog/a2a-v1-0-a-builder-s-guide-part-2-migration-security-and-production)). Staying on 0.3 is defensible if documented as a deliberate choice, but a grader reading 2026 docs will expect 1.0 terms, and migration also interacts with the ADK 1.x vs 2.x decision. Independent of version, the notes list probable conformance gaps to verify: `securitySchemes` in each card matching the bearer auth, `capabilities.streaming` with live status and artifact updates, patches and plans returned as Artifacts, an `input-required` round trip resumed on the same taskId, UI cancel wired to `CancelTask` (success is not guaranteed, so show the resulting state), a declared custom extension for trace and worktree metadata, and durable SQL task stores in place of in-memory ones ([A2A spec](https://a2a-protocol.org/latest/specification/)). The official A2A Inspector adds card validation, raw wire-traffic view and task and push-config management that the run-centric explorer likely lacks ([a2a-inspector](https://github.com/a2aproject/a2a-inspector)). No open-source multi-agent coding project using A2A was verified, so H.E.X Mind has no direct A2A-coding peer to copy.

## Prioritized adoption list

Effort is S (up to 1 day), M (2 to 4 days), L (about a week or more), a rough student-scale judgement rather than a sourced figure, except where the notes gave days. "Allowed" means achievable with ADK, CrewAI, A2A and plain Python/Docker/Chroma; every item below clears the framework restriction, so the risk column is about technical and version risk. Each item must first be checked against the repo, since all are inferred gaps.

Items 1 to 4 are the recommended next build: they are low-risk, independent of the A2A and ADK version questions, and address the failure categories (verification, specification) that MAST and the Agentless and AgentCoder results identify. Item 5 comes next because it is cheap and is what A2A graders will probably check. Items 14 and 17 are higher risk because they depend on unresolved version questions or unverified platform behaviour. The notes advise skipping enterprise security analyzers, Jules-style VM-per-task (defer to P8 per the project plan), RL model training, and Letta or Graphiti memory stacks, for which no coding evidence was found. Gaps in the research itself: Roo Code, Windsurf, Devin internals and Claude Code auto-compact had only secondary or no coverage; the A2A TCK and the Inspector's signature support were not confirmed; and how ADK maps INPUT_REQUIRED should be answered from ADK source before building item 5.

## Conclusion

The comparison reframes H.E.X Mind's position: its architecture is not behind the state of the art; its measurement and single-agent mechanics probably are. Systems that report credible gains do so by grounding every loop in executed tests, applying edits robustly, bounding context, and publishing a repeatable number, and those techniques are framework-agnostic, so the course restriction to CrewAI and ADK costs nothing here. The most distinctive thing H.E.X Mind can claim, A2A-aware cross-agent tracing, is also where no surveyed peer was found, which makes finishing the A2A conformance work and the OTLP alignment worth more than adding agents.

The unresolved items are decisions as much as research gaps: which a2a-sdk line (0.3 or 1.x) and which ADK line (1.x or 2.x) the project commits to determines the effort of items 3, 5, 13 and 14. Benchmark figures in this area are unstable enough (SWE-bench Verified retired by one lab, conflicting tool scores, shifting free-tier limits) that a small, frozen, self-run suite is the only number worth quoting in the course report. Before building anything, diff this list against the repo, since each "missing" feature may already exist.
