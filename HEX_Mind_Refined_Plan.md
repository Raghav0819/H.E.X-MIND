# H.E.X Mind — Refined Implementation Plan

> **Status:** Working source of truth for Claude Code and the team. Supersedes `HEX_Mind_Latest_Plan_for_Claude_Code.md` where the two differ (the original is kept for reference and for the course-requirement wording).
> **Product:** H.E.X Mind (Hivemind Execution X), an agent-native Electron IDE with live multi-agent observability.
> **Demo target:** a to-do app. The IDE and the agent workflow are the product.
> **Hard rules:** no Jev anywhere. No fabricated agent activity, tokens, cost or latency. Generated code is untrusted.

## 0. What changed from the original plan (and why)

| # | Issue in original | Refinement |
|---|---|---|
| 1 | Week 1 asks for Monaco + DB + provider call, while §19 says milestone 1 is only Electron + health check. | Split into **M0 (skeleton)** and **M1 (foundation)**. See §9. |
| 2 | LangGraph and CrewAI both orchestrate, so ownership of control flow was unclear. | **LangGraph owns all control flow.** CrewAI is used only to define the Planner/Coder/Reviewer *roles*; each LangGraph node runs a single-agent, single-task Crew. No CrewAI hierarchical process. |
| 3 | CrewAI calls LLMs through its own client, which would bypass our provider adapters, fallback and telemetry. | Every LLM call (Router, CrewAI agents, judge) goes through one `ProviderRouter`. CrewAI agents get a custom `BaseLLM` wrapper that delegates to it. **Spike in M3** against the pinned CrewAI version. |
| 4 | Unclear whether Electron main or the backend reads and writes workspace files, so path checks would be duplicated. | **The backend is the single file authority.** Electron main only runs the native folder picker and hands the path to the backend. One path guard in one language. |
| 5 | "Show diff before applying", "don't overwrite user changes" and "Git recovery" had no concrete mechanism. | **Per-run Git worktree.** Agents edit an isolated worktree, never the user's files. The user approves the diff, it is applied with stale-file detection, and a checkpoint commit makes it revertible. See §5. |
| 6 | Loopback binding was the only backend protection. Any local web page can call `localhost`. | Per-session **bearer token** generated by Electron main and passed to the backend. Strict CORS. See §7. |
| 7 | High-complexity tasks "run in parallel", but several Coders editing one tree will conflict. | Planner declares `target_files` per task. Tasks run in parallel only when their file sets are disjoint; otherwise they are serialized. Default worker concurrency is 2. |
| 8 | The timeline was sequential but there are 3 owners. | Weekly plan has **parallel tracks per owner**, coupled through contracts frozen early (§4). |
| 9 | Evaluation data collection only started in Week 7. | Labeled routing set starts in **M2**; benchmark tasks are fixed by **M4**; telemetry is logged from M1. |
| 10 | Sections 10/18 (security) and 15/20 (DoD) were duplicated. | Merged into §7 and §11. |
| 11 | Explicit chat mode and the Router could disagree. | **The user's explicit mode wins.** In Ask mode no file writes can happen, whatever the Router says. |
| 12 | "Run tests in isolation" had no concrete mechanism. | Docker sandbox with no network, CPU/mem/pid/time limits, and **allowlisted commands from a project profile**, never LLM-generated commands. See §7. |
| 13 | No supervision view beyond the game map. | Adopted from [Orchestrator.inc](https://github.com/OrchestratorInc/agent-orchestrator), our reference design: **attention columns** (Working / In review / Needs you / Ready to apply) and a **"Needs you" queue**, both derived from backend state. See §3.5. We deliberately do **not** adopt a worktree per task (it needs a merge step; too much for 8 weeks) or wrapping external agent harnesses (Claude Code, Codex…), which would block per-call telemetry, provider comparison and the CrewAI course requirement. |

## 1. Architecture (single backend process)

```text
Electron main ── folder picker, window lifecycle, spawns/monitors backend (packaged), session token
   │ preload (contextBridge: hex.pickWorkspace, hex.backend {url, token}, hex.openExternal)
   ▼
React + TS renderer (Vite) ── Monaco, explorer, chat, diff, runs, metrics, Phaser map (lazy)
   │ REST + WebSocket (Bearer token)
   ▼
FastAPI backend (127.0.0.1:8765)
   ├── api/          REST + WS
   ├── context/      ContextManager (conversation / project / execution / code)
   ├── graph/        LangGraph: router → dispatch → plan → execute → review → finalize
   ├── agents/       CrewAI role definitions (Planner, Coder, Reviewer)
   ├── providers/    ProviderRouter + adapters (Ollama, Groq, Gemini), quota, fallback, cost table
   ├── blackboard/   Task store, atomic claim, leases, worker pool (asyncio)
   ├── workspace/    path guard, git worktrees, diff/apply/revert
   ├── sandbox/      Docker runner for allowlisted checks
   ├── mcp_server/   MCP workspace server (stdio subprocess), the only tool surface agents get
   ├── memory/       ChromaDB (embedded): coding_standards, agent_self_logs
   ├── events/       append-only event log + in-process pub/sub → WS
   └── evaluation/   benchmark runner, LLM judge, sklearn baseline
   ▼
PostgreSQL (Docker Compose, port 5433). Authoritative state.
ChromaDB (embedded, on-disk). Retrieval only, never lifecycle state.
Docker. Sandbox containers for tests.
```

No Redis, no message broker, no microservices. In-process pub/sub is enough for one backend.

## 3. Core flows

### 3.1 Message → run

```text
POST /api/conversations/{id}/messages {content, mode: ask|edit|auto}
  → persist message
  → ContextManager.build()       (budgeted; see 3.4)
  → Router (LLM, structured)     → RouterDecision (Pydantic)
  → Policy (deterministic):
        mode=ask                  → answer only (no write tools bound)
        request_type=clarification→ reply with question, no run
        question                  → answer node
        code_edit / new_workflow  → create Run(parent_run_id = last run in conversation)
  → LangGraph executes the run; every transition emits events
```

**Route policy (initial heuristic; to be tuned with M7 data):**

| Complexity | Path |
|---|---|
| low | Coder → sandbox checks → (Reviewer only if checks fail or the change touches >2 files) → awaiting approval |
| medium | Planner → Coder(s) → sandbox checks → Reviewer → awaiting approval |
| high | Planner (decompose with deps + target_files) → parallel Coders on disjoint files → checks → Reviewer → awaiting approval |

**Router safeguards:** JSON schema output, then Pydantic validation, then one repair retry. If it still fails, or `confidence < 0.6`, fall back to a deterministic route: `medium`, planning and review on, and in `auto` mode ask for clarification instead of editing. Log the decision, rationale, provider, any fallback, and the final outcome to `router_decisions`.

### 3.2 Run state machine

```text
queued → routing → planning → executing → checking → reviewing → awaiting_approval → applied
                                  ↑            │            │                       ↘ rejected
                                  └── changes_requested ←───┘ (max 2 loops → blocked)
any state → failed | cancelled
applied → reverted
```

M2 note: while the worker nodes are stubs, runs end in `completed` with a `run_completed {stub: true}` event and no diff. From M3, runs end in `awaiting_approval`.

### 3.3 Task lifecycle (Blackboard)

`pending → claimed → running → review → completed`, with `failed`, `changes_requested → pending (retry)`, `blocked` (dependency failed or retries exhausted).

**Atomic claim:**
```sql
UPDATE tasks SET status='claimed', claimed_by=:worker, claimed_at=now(),
       lease_expires_at=now()+interval '5 min', attempts=attempts+1
WHERE id = (
  SELECT t.id FROM tasks t
  WHERE t.run_id=:run AND t.status='pending'
    AND NOT EXISTS (SELECT 1 FROM task_dependencies d JOIN tasks p ON p.id=d.depends_on
                    WHERE d.task_id=t.id AND p.status<>'completed')
  ORDER BY t.priority, t.created_at
  FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;
```
A lease reaper requeues expired claims while `attempts < max_attempts`, and otherwise marks them `blocked`. The file-disjointness check (refinement #7) runs in the same transaction against the `target_files` of currently `running` tasks.

### 3.4 Context manager

There are four separate sources, each with its own token budget (defaults, tunable):

| Source | Budget | Content |
|---|---|---|
| Conversation | 20% | rolling summary + last N turns + messages explicitly referenced |
| Project | 10% | `HEXMIND.md` project instructions (if present), stack, file tree (trimmed) |
| Execution | 15% | last runs in this conversation: status, changed files, review findings, errors |
| Code | 55% | **current** contents of files: mentioned by the user → changed in prior runs → keyword/symbol search hits |

Files are always re-read from disk at build time. History never stands in for current code. The rolling summary is regenerated after each completed run. Secrets are redacted before anything reaches a model (`.env*` files are excluded entirely).

### 3.5 Attention model (supervision)

**Columns.** Every run sits in one attention column. The **backend derives it** from authoritative run, task and review state; the renderer never computes it.

| Column | Derived when |
|---|---|
| Working | run status ∈ {queued, routing, planning, executing, checking} |
| In review | run status = reviewing |
| Needs you | the run has at least one open attention item (below); this takes precedence over the other columns |
| Ready to apply | status = awaiting_approval, the latest review is `approved`, and all checks passed |
| Done (hidden by default) | applied / rejected / reverted / cancelled / failed with no open items |

**Attention items** form the "Needs you" queue. Each item is `{run_id, task_id?, kind, message, created_seq}`.

| Kind | Raised when | Resolved when |
|---|---|---|
| `apply_conflict` | an approved file's workspace hash ≠ `base_hash` (§5 step 6) | the file is reloaded, overwritten or rejected |
| `task_blocked` | a task hits `blocked` (retries or review loops exhausted, or a dependency failed) | the task is retried or the run is cancelled |
| `clarification_requested` | the Router policy returns a clarification | the user replies in the conversation |
| `provider_unavailable` | no eligible provider remains after fallback | a later call succeeds or the run is cancelled |
| `run_failed` | the run enters `failed` | the user dismisses it or retries |
| `approval_pending_with_findings` | the run is `awaiting_approval` while the reviewer has open findings | the run is approved, rejected or re-reviewed |

**Rules**
- **No new event types.** Items are derived from existing events (§4.1) and current state, so they survive reconnects through the snapshot like everything else.
- **One function.** `derive_attention(run, tasks, reviews, file_changes, latest_events)` in `apps/backend/app/attention/` is pure and unit-tested. Its output is embedded in the run snapshot and run list, and served by `GET /api/attention`.

## 4. Contracts (freeze early; owners develop against them in parallel)

### 4.1 Event envelope (draft in M2, **frozen v1 at end of M3**)

```json
{
  "schema_version": 1,
  "event_id": "uuid",
  "run_id": "uuid",
  "seq": 18,
  "ts": "2026-10-23T10:00:00Z",
  "type": "task_started",
  "agent_id": "coder_01",
  "task_id": "uuid|null",
  "payload": {}
}
```

- `seq` is per-run and gap-free. It's assigned in the same DB transaction as the event insert (`UPDATE runs SET last_event_seq = last_event_seq + 1 RETURNING`). Events are published to WS **after commit**.
- Types: `run_created, run_status_changed, router_decided, task_created, task_claimed, task_started, tool_called, llm_call_started, llm_call_completed, provider_fallback, check_started, check_completed, review_started, review_completed, task_completed, task_failed, task_blocked, diff_ready, run_completed, run_failed, run_cancelled`.
- Every type has a Pydantic payload model, and TS types are **generated** from them (`datamodel-code-generator` → JSON Schema → `json-schema-to-typescript`) so the two sides cannot drift.

**Client reconciliation:** `GET /api/runs/{id}/snapshot` returns `{last_seq, run, tasks, agents, metrics}`. The client then opens `WS /ws/runs/{id}?after_seq=last_seq`, and the server replays from the DB before going live. The client drops `seq ≤ applied`, buffers ahead-of-order events, and refetches the snapshot if a gap persists for more than 2 s or after a reconnect.

### 4.2 REST (v1)

```
GET  /api/health                         → {status, db, docker, providers:{ollama,groq,gemini}}
POST /api/projects                       {workspace_path} → project
GET  /api/projects/{id}/tree             ?path=
GET  /api/projects/{id}/file             ?path=        (read)
PUT  /api/projects/{id}/file             {path, content, base_hash}  (user edits from Monaco; 409 if stale)
POST /api/projects/{id}/conversations
GET  /api/conversations/{id}/messages

GET  /api/runs?project_id=&q=            (history)
GET  /api/runs/{id}  | /snapshot | /events?after_seq= | /metrics | /diff
                                         (run list and snapshot include the derived `attention` column + items, §3.5)
GET  /api/attention?project_id=          → open "Needs you" items across the project's runs
POST /api/runs/{id}/approve              {files?: [...]}   → apply
POST /api/runs/{id}/reject
POST /api/runs/{id}/revert
POST /api/runs/{id}/cancel
POST /api/tasks  · GET /api/tasks?run_id= · POST /api/tasks/{id}/claim · POST /api/tasks/{id}/review

```

### 4.3 Provider interface

```python
class LLMRequest(BaseModel): messages; json_schema: dict|None; max_tokens; temperature; purpose: str  # router|planner|coder|reviewer|judge
class LLMResult(BaseModel): provider; model; content; parsed: dict|None; input_tokens|None; output_tokens|None;
                            latency_ms; est_cost_usd|None; attempts; fallback_from: str|None; error: str|None
class ProviderAdapter(Protocol):
    name: str
    async def health(self) -> ProviderHealth
    async def complete(self, req: LLMRequest, model: str) -> LLMResult
```

`ProviderRouter.complete(req, ctx)` picks the provider by policy (complexity × availability × quota × budget). It retries 429/timeouts with bounded exponential backoff (max 3), falls back through an ordered eligible list (Ollama only if `health()` reports the model installed), writes `llm_calls`, and emits `llm_call_*` / `provider_fallback`. Prices live in `providers/pricing.yaml` with a `last_verified` date. Missing token counts stay `null` and are never estimated silently.

### 4.4 `add_task()` (Blackboard, shared by Planner and Router)

```python
async def add_task(run_id, title, description, acceptance_criteria: list[str],
                   target_files: list[str], depends_on: list[UUID] = [], priority: int = 0,
                   complexity: Literal["low","medium","high"]) -> Task
```
This rejects duplicate titles or near-duplicates within a run (normalized title match), which feeds the Planner PEAS "duplicate rate" metric.

## 5. Workspace, edits and recovery

1. **Open workspace:** native picker → `POST /api/projects`. The backend canonicalizes the path (`realpath`) and stores it. If the folder isn't a Git repo, the user is asked once to run `git init` plus an initial commit. Agent edits require Git.
2. **Run start:** `base = git stash create` (a commit of the current working state, including uncommitted changes, without touching the user's files), or `HEAD` if the tree is clean. Create the worktree at `%APPDATA%/hexmind/worktrees/<run_id>` on branch `hexmind/run-<short_id>` from `base`. This lives outside the user's folder.
3. **Agents** only read and write inside that worktree, through MCP tools.
4. **Checks** run in the Docker sandbox with the worktree mounted.
5. **Diff:** worktree vs `base`, file by file → `file_changes` (+ `base_hash` per file) → `diff_ready` event → Monaco diff view.
6. **Approve:** create the checkpoint `pre_apply = git stash create` (or HEAD). For each approved file, if the current workspace hash ≠ `base_hash`, flag a **conflict** (show it, don't overwrite). Otherwise write the file. Record `pre_apply` on the run.
7. **Revert:** restore the files touched by the run from `pre_apply`, with the same stale check.
8. **Cleanup:** remove the worktree after apply, reject or cancel. Keep the branch for history (pruning is optional).

**Path guard (one implementation, heavily tested):** resolve `realpath`, require it to be under the root, reject `..`, absolute paths, drive letters, UNC paths, NTFS alternate data streams (`:`), reserved names (`CON`, `NUL`…), and symlinks escaping the root. Writes are denied to `.git/`, `.env*` and `node_modules/`.

## 6. Agents

| Agent | Input | Tools (MCP) | Output (Pydantic) |
|---|---|---|---|
| Router | context bundle + message | none | `RouterDecision {request_type, complexity, confidence, reason, execution_strategy, requires_planning, requires_review}` |
| Planner | request + context | `list_files, read_file, search_code` (read-only) | `Plan {tasks:[{title, description, acceptance_criteria, target_files, depends_on, complexity}]}`, inserted via `add_task()` |
| Coder | claimed task + current file contents + RAG standards | `read_file, search_code, write_file, apply_patch, run_check(name)` (worktree only) | `CoderResult {changed_files, summary, checks_run:[{name, exit_code, summary}], status, error}` |
| Reviewer | task + acceptance criteria + diff + check results | `read_file, run_check(name)` | `Review {verdict: approved\|changes_requested\|blocked, findings:[{file, line, severity, message}]}` |

- ReAct-style loop for Planner/Coder, with a bounded number of tool steps (default 15).
- Coder–Reviewer loop: max 2 `changes_requested` rounds, then `blocked` and escalate to the user.
- Self-logs: after each task the agent writes a short structured log (`what tried / what failed / outcome`) to the Chroma `agent_self_logs` collection, keyed by run, task and role. The Coder retrieves top-k relevant self-logs plus `coding_standards`.
- `coding_standards` is seeded from `docs/standards/*.md` (TS/React, Python, testing, security).

**MCP server (`hexmind-workspace`, Python `mcp` SDK, stdio):** started by the backend per run, bound to that run's worktree root. `run_check(name)` accepts only names defined in the project profile (`.hexmind/profile.yaml`, e.g. `test: npm test`, `lint: npm run lint`, `typecheck: npx tsc --noEmit`). Models choose a name, never a command line.

## 7. Security and reliability rules

**Electron:** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, strict CSP, `setWindowOpenHandler` → `shell.openExternal` only for `https:` URLs, no `remote`, and IPC payloads validated in main. The preload exposes only `pickWorkspace()`, `getBackend(): {url, token}`, `openExternal(url)`, `appInfo()`.

**Backend access:** bound to `127.0.0.1` only. Every REST/WS request needs `Authorization: Bearer <session token>` (WS takes it as a query parameter or first message). CORS is limited to the renderer origin. In dev the token comes from `.env`; when packaged, main generates it and passes it to the backend process via env.

**Sandbox:** `docker run --rm --network none --cpus 1 --memory 1g --pids-limit 256 --read-only --tmpfs /tmp -v <worktree>:/work -w /work hexmind-runner-node:20 <profile command>` with a 120 s timeout, killed on expiry. Dependency install (`npm ci` / `uv sync` from the lockfile) is a separate step with network enabled. It only runs on user approval, and again only when the lockfile hash changes.

**Secrets:** API keys exist only in backend env. They never reach the renderer, the DB, logs or prompts. A redaction filter covers log records and the context builder. Settings show *configured / missing*, never the values. Commit `.env.example` only.

**Model output** never directly authorizes anything. Writes are limited to the worktree, commands to profile names, and applying changes needs a user click.

**Cancellation:** `POST /runs/{id}/cancel` sets a flag checked between graph nodes and tool steps, kills any running sandbox container, and marks pending tasks `cancelled`.

## 9. Milestones

Each milestone ends with: code runs, tests/type checks/builds pass, a short report (changed files, commands, results, limitations, next step). The team builds the **integration slice** in this order, and owners prepare their next piece in parallel against the frozen contracts.

### M0 — Skeleton (first milestone for Claude Code)
- Root `package.json` (npm workspaces), `apps/desktop` (electron-vite: main, preload, renderer), `apps/backend` (uv, FastAPI).
- `GET /api/health` → `{status:"ok", version}`, with bearer token and CORS.
- Preload exposes `getBackend()`. The renderer shows an IDE frame (top bar, activity bar, empty editor area, right and bottom panels as placeholders) and a backend status pill: connecting, connected or unreachable (with a retry option).
- Design tokens (dark-first), Lucide icons.
- `.gitignore`, `.env.example`, README (dev setup), `git init`.
- Tests: pytest (health + auth rejects a missing token), Vitest (status pill states), `tsc --noEmit`, `electron-vite build`.
- **Exit:** `npm run dev` + `uv run uvicorn …` opens the window, which shows *Connected*. Stopping the backend shows *Unreachable*.

### M1 — Foundation (Week 1)
- Docker Compose (Postgres :5433), SQLAlchemy + Alembic, all §8 tables.
- Workspace: folder picker → project, path guard (+ adversarial tests), file tree, Monaco with tabs and save (`base_hash` stale check).
- Event log with per-run seq + `GET /events`.
- `ProviderRouter` with **one** adapter (Groq or Ollama), with the `llm_calls` row written.
- **Exit:** open a folder, edit and save a file, create a dummy run whose events persist, make one logged LLM call.

### M2 — Chat, Router, Context (Week 2)
- Persistent conversations and messages, chat panel with Ask/Edit/Auto modes.
- ContextManager (§3.4), Router with structured output and fallback, `router_decisions`.
- LangGraph skeleton with the real routing edges. Worker nodes are stubs that emit real events for stub work, clearly labeled as stubs in the UI.
- Event schema v1 draft plus TS type generation.
- Start `routing_labels`: ≥ 150 labeled prompts, two labelers on a 30-prompt overlap to measure agreement.
- **Exit:** Ask-mode questions are answered with project context, a follow-up message links to the same conversation, and router decisions are validated and logged.

### M3 — Worker swarm + safe execution (Week 3)
- Blackboard `add_task`, atomic claim, leases, worker pool. A **concurrency test** where 10 workers race for 50 tasks gives zero double claims.
- Git worktree lifecycle, MCP workspace server, sandbox runner image + profile checks.
- CrewAI Planner/Coder/Reviewer via the `BaseLLM` wrapper (spike first, see risk R1). Chroma `coding_standards` + self-logs.
- **Event schema v1 frozen.**
- **Exit:** "Build a to-do app…" produces a plan, code in the worktree, passing checks, a review verdict and a `diff_ready` event. It's fine if the UI is still plain.

### M4 — Providers and fallback (Week 4)
- Groq, Gemini and Ollama adapters, health checks, quota tracking (per-provider counters + 429 headers), pricing table.
- Selection policy + fallback chain, `provider_fallback` events.
- Fault-injection tests: forced 429, timeout, Ollama model missing.
- Fix the **benchmark task set** (≥ 12 tasks with acceptance tests and expected complexity).
- **Exit:** a forced quota exhaustion mid-run falls back and finishes, and the fallback can be traced in DB and events.

### M5 — Live map and observability (Week 5)
- Event store in the renderer (snapshot + WS + reconciliation per §4.1).
- Compact agent status list + task board (the primary view).
- Phaser scene (lazy-loaded): stations, agents, task tiles, transitions driven only by events, honoring reduced motion.
- Metrics panel: routing, provider/model, tokens, cost, latency, retries, checks, review.
- Attention model (§3.5): `derive_attention` + `GET /api/attention`. The **attention board** (Working / In review / Needs you / Ready to apply) becomes the primary run view next to the status list. Add a **Needs you** tab in the bottom panel and a badge count in the top bar.
- Tests: reconciliation unit tests (duplicates, out-of-order, gaps, reconnect) plus a replay test that feeds a recorded event log and checks the final UI state, **including attention columns**, matches the snapshot. Add a unit-test table for every attention kind (raise and resolve).
- **Exit:** the map matches backend state during a real run and after a forced WS disconnect.

### M6 — Context-aware IDE loop (Week 6)
- Diff review (per-file approve/reject), apply with conflict detection, revert, cancel.
- Follow-up runs that use `parent_run_id` and prior-run context. Run history with search.

## 12. Risks

| ID | Risk | Mitigation |
|---|---|---|
| R1 | CrewAI's LLM layer can't be cleanly routed through our ProviderRouter. | Spike in week 2. Fallback plan: call the CrewAI Agent with a LiteLLM-compatible custom endpoint, or implement the three roles as LangGraph nodes with CrewAI-style role prompts (and record the deviation). |
| R2 | A 7B local model is too weak for multi-file edits. | That's an expected finding, not a failure. Keep the Ollama route to low-complexity tasks by default and report it. |
| R3 | Groq/Gemini free-tier limits during the benchmark. | Quota tracker, spread runs over days, cache nothing that would distort results. |
| R4 | Docker bind-mount speed on Windows. | Keep worktrees on a local NTFS path and pre-bake runner images with deps for the demo app. |
| R5 | UI scope creep (map polish). | The status list, attention board and task board come first. The map stays secondary and time-boxed. The attention model adds no event types, so it doesn't widen the frozen contract. |
| R6 | Packaging Postgres with the desktop app. | Out of scope. Document that Compose is required. |
